# Brain: 02 Create Project Flow

This document provides the technical implementation plan for the "Create Project" user flow, as described in `walkthrough/02_Create_Project_Flow.md`.

## 1. Data Models

### Project
- `id`: UUID (Primary Key, generated locally)
- `name`: String (User-provided project name, e.g., "My Awesome Project")
- `repo_name`: String (Sanitized name for GitHub, e.g., "my-awesome-project")
- `repo_owner`: String (User's GitHub username)
- `github_repo_id`: Long (The numeric ID from GitHub API response)
- `created_at`: Timestamp
- `updated_at`: Timestamp

## 2. Core Logic and Algorithms

### 2.1. Project Name Sanitization

- **Input:** User-provided project name string.
- **Process:**
    1. Convert to lowercase.
    2. Replace spaces and underscores with hyphens (`-`).
    3. Remove any characters that are not alphanumeric, hyphens, or dots.
    4. Collapse multiple consecutive hyphens into a single hyphen.
    5. Trim leading/trailing hyphens.
- **Output:** A URL-friendly slug for the repository name.
- **Example:** "My Awesome Project!" -> "my-awesome-project"

### 2.2. GitHub Repository Name Uniqueness Check

- **API Endpoint:** `GET /repos/{owner}/{repo}`
- **Logic:**
    1. After sanitizing the project name, call the GitHub API to check if a repository with that name already exists for the authenticated user.
    2. If it returns `200 OK`, the repository exists.
    3. If it returns `404 Not Found`, the name is available.
- **Conflict Resolution:**
    1. If the name exists, append a suffix (e.g., `-2`).
    2. Re-run the uniqueness check with the new name (e.g., `my-awesome-project-2`).
    3. Repeat with incrementing numbers (`-3`, `-4`, ...) until an available name is found.
    4. The final proposed name must be confirmed by the user via a UI dialog.

## 3. API Interactions (GitHub)

The application will use a stored OAuth token for all GitHub API interactions.

### 3.1. Create Repository

- **API Endpoint:** `POST /user/repos`
- **Request Body:**
    ```json
    {
      "name": "my-awesome-project",
      "description": "Project generated by GhostBuilder.",
      "private": true,
      "auto_init": false
    }
    ```
- **Error Handling:**
    - `401 Bad credentials`: The OAuth token is invalid or expired. Trigger re-authentication.
    - `422 Unprocessable Entity`: Validation failed (e.g., name already exists, though this should be pre-empted by the uniqueness check). Log the error and inform the user.
    - Other server errors (`5xx`): Implement a retry mechanism with exponential backoff.

### 3.2. Create Initial Commit

This will be a multi-step process using the Git Data API, as we are not using a local git client.

1.  **Create Blobs:** For each file to be added (`README.md`, `.gitignore`, `project_state.json`), make a `POST /repos/{owner}/{repo}/git/blobs` call with the file content. This returns a SHA for each file blob.
2.  **Create Tree:** Make a `POST /repos/{owner}/{repo}/git/trees` call with the list of file paths and their corresponding blob SHAs. This returns a tree SHA.
3.  **Create Commit:** Make a `POST /repos/{owner}/{repo}/git/commits` call, providing the tree SHA and a commit message (e.g., "Initial commit from GhostBuilder"). This returns a commit SHA.
4.  **Update Reference:** Make a `PATCH /repos/{owner}/{repo}/git/refs/heads/main` call to point the `main` branch to the new commit SHA.

- **Error Handling:** If any step in this chain fails, the process should be considered failed. The app should attempt to delete the created repository (`DELETE /repos/{owner}/{repo}`) to clean up, and then report the failure to the user. Project creation is blocked until this succeeds.

## 4. UI Component States and Interactions

-   **Project Creation Dialog:**
    -   **Initial State:** Text input for "Project Name", "Create" button (disabled), "Cancel" button.
    -   **Validation:** "Create" button becomes enabled only when the project name is not empty.
    -   **Loading State:** After tapping "Create", show a loading indicator/spinner. Disable input and buttons.
-   **Repo Name Conflict Dialog:**
    -   **State:** Displays the conflicting name and the suggested new name (e.g., "my-awesome-project-2"). Provides "Confirm" and "Cancel" buttons.
-   **Error State:**
    -   If any part of the GitHub interaction fails, display a clear error message to the user (e.g., "Failed to create GitHub repository. Please check your connection and try again.").

## 5. First-Time Setup (GitHub OAuth)

-   **Trigger:** This flow is triggered if the app does not have a valid GitHub OAuth token stored locally.
-   **Mechanism:**
    1.  Use the Android `Custom Tabs` to open a browser to the GitHub OAuth authorization URL.
    2.  The app will register a custom URI scheme (e.g., `ghostbuilder://oauth/callback`).
    3.  When the user authorizes the app on GitHub, GitHub will redirect to this custom URI with a temporary `code`.
    4.  The app will capture this `code` from the intent.
    5.  The app will exchange the `code` for a permanent OAuth token by making a secure server-to-server call from its backend (the client app should not handle the client secret).
-   **Token Storage:** The retrieved OAuth token will be stored securely on the device using Android's `EncryptedSharedPreferences`.
